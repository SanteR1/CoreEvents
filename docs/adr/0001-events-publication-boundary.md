# ADR 0001: Граница публикации интеграционных событий

## Статус

Принято, 10.11.2026

## Контекст

В сервисе `Events` интеграционные события попадали в Outbox двумя путями: из хендлеров доменных событий (`IPreCommitHandler`) и напрямую из хендлеров команд. При переносе резервации мест на доменные события новый путь добавили, а старый не удалили. В результате:

- `BookingReservationAccepted` и `BookingReservationRejected` записывались в Outbox дважды;
- в агрегат `Event` пришлось добавить `SeatsReservationRejectedDomainEvent`, хотя при отказе его состояние не меняется;
- хендлерам доменных событий не хватало контекста процесса (`CorrelationId`, `CausationId`, `ExpiresAt`, `SeatReservation`).

## Решение

> Факт изменения состояния агрегата публикуется через хендлер доменного события (`IPreCommitHandler`).
> Результат процесса (ответ саги) публикуется явно из хендлера команды.

Для каждого типа интеграционного события существует ровно один путь публикации.

| Тип                | Примеры                                                                                  | Путь                                                      |
| ------------------ | ---------------------------------------------------------------------------------------- | --------------------------------------------------------- |
| Lifecycle агрегата | `EventCreated`, `EventUpdated`, `EventCancelled`                                         | `Event` → доменное событие → `IPreCommitHandler` → Outbox |
| Ответ саги         | `BookingReservationAccepted`, `BookingReservationRejected`, `BookingReservationReleased` | хендлер команды → Outbox                                  |

### Как выбрать путь для нового события

- Это факт, произошедший с агрегатом, независимо от того, кто его инициировал? Доменное событие и `IPreCommitHandler`.
- Это ответ на запрос или шаг процесса, которому нужен контекст запроса? Хендлер команды.

### Правила

- Команды lifecycle (`Create/Update/CancelEvent`) не обращаются к Outbox.
- Хендлеры доменных событий только транслируют доменное событие в контракт и не содержат бизнес-логики.
- Агрегат поднимает доменные события только при изменении своего состояния.
- Запись в Outbox выполняется внутри транзакции, до коммита. `IPostCommitHandler` в Outbox не пишет.
- Бизнес-отказ возвращается значением, а не исключением: исключение откатит транзакцию вместе с записью в Outbox.

### Причина отказа резервации

`Event.TryReserveSeats` возвращает `ReserveSeatsResult` (`None = 0`, `Reserved`, `EventInactive`, `InsufficientSeats`). Значение `None = 0` нужно, чтобы `default` не выглядел как успех. Слой `Application` переводит результат в контрактный `ValidationFailureReason` через `ReserveSeatsResultMapper`, доменный enum наружу не уходит.

## Последствия

**Плюсы:**

- один путь публикации на каждый тип события, дубли исключены;
- домен без псевдособытий;
- запись в Outbox атомарна с изменением данных.

**Минусы:**

- в сервисе два механизма публикации, и соблюдение правила границы для новых сценариев держится на дисциплине разработчиков и код-ревью.

## Рассмотренные альтернативы

- **Всё через доменные хендлеры.** Отклонено: ответам саги нужен контекст процесса, а отказы без изменения состояния пришлось бы выражать искусственными доменными событиями.
- **Всё из хендлеров команд.** Отклонено: события lifecycle потеряются при появлении новой точки входа, которая изменяет агрегат.
- **Отдельный агрегат резервации** (`Reservation`), у которого переходы состояний станут доменными событиями, и тогда все события пойдут через доменные хендлеры. Отложено: требует отдельного рефакторинга, к которому можно вернуться позже.

## Способы закрепить границу в коде

Правило сейчас держится на код-ревью и интеграционных тестах Outbox. Усиление отложено, потому что lifecycle-событий три и граница меняется редко. Если путаница начнёт возникать на практике, варианты по возрастанию цены:

- **Маркер `IEntityLifecycleEvent` и отдельный метод Outbox** (например, `AddLifecycleEvent<T> where T : IEntityLifecycleEvent`). Компилятор не даст опубликовать из доменного хендлера событие саги. Работает, только если общий `AddIntegrationEvent` недоступен доменным хендлерам.
- **Раздельные интерфейсы Outbox** для доменных хендлеров и хендлеров команд. Хендлер физически не получает чужой метод.
- **Мапперы `IIntegrationEventMapper`**, при которых доменные хендлеры не знают про Outbox, а запись делает инфраструктура. Самый чистый вариант, но требует новой инфраструктуры.

## Контроль

- Интеграционные тесты проверяют отсутствие дублей в Outbox для покрытых сценариев бронирования (успех, нехватка мест, неактивное событие).
- Тесты полноты маппинга (`ReserveSeatsResultMapperTests`) проверяют исчерпывающую обработку всех исходов резервации.
- Соблюдение границы для новых событий контролируется на код-ревью по критериям этого ADR.
